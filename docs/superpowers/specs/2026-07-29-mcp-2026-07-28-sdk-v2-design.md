# MCP spec 2026-07-28 via the v2 TypeScript SDK — design

Date: 2026-07-29
Status: approved, ready for planning

## Goal

Adopt MCP spec `2026-07-28` across both of our MCP surfaces by replacing our
hand-rolled protocol core with the v2 TypeScript SDK
(`@modelcontextprotocol/server@2.0.0`), while keeping every existing client —
all of which speak 2025-era revisions — working unchanged.

This mirrors sibling project `buildinternet/sunny`
([issue #773](https://github.com/buildinternet/sunny/issues/773),
[PR #774](https://github.com/buildinternet/sunny/pull/774)), but the mechanism
differs: sunny was upgrading an SDK they already had, whereas we are adopting
one for the first time.

## What exists today

Two surfaces share one core, and the core is entirely ours:

- **`packages/uploads/src/mcp/server.ts`** — ~190 hand-written lines.
  `createMcpServer({ serverInfo, tools, apiUrl })` returns an object with a
  single `handleLine(line)` method: one JSON-RPC message in, one serialized
  response (or `undefined` for notifications) out. Runtime-agnostic by design.
- **`packages/uploads/src/mcp/stdio.ts`** — a 14-line readline loop over
  `handleLine`, driving the published `uploads mcp` command
  (`packages/uploads/src/commands/mcp.ts`).
- **`apps/mcp`** — the hosted Hono worker on `agents.uploads.sh` (alternate
  `mcp.uploads.sh`). Already stateless: fresh server per request, no session
  id, plain-JSON replies, 405 on GET/DELETE. Calls the same `handleLine`.

Tools are authored declaratively against our own `McpTool` interface
(`{ name, description, inputSchema, handler }`) with **hand-written JSON
Schema**: 21 tools in `packages/uploads/src/mcp/tools.ts` (1,412 lines) and 17
in `apps/mcp/src/tools.ts` (1,048 lines), sharing the argument helpers in
`packages/uploads/src/mcp/args.ts`.

Test coverage is 126 tests: 62 in `packages/uploads/test/mcp.test.ts`, all
funnelled through one `rpc()` helper that wraps `handleLine`; 64 across the
`apps/mcp` suites, which drive real HTTP `Request`s and never touch
`handleLine`.

No MCP SDK is currently a dependency of anything.

## Why adopt the SDK rather than extend the hand-rolled core

The historical argument for hand-rolling was zero dependencies in the
published CLI. That argument is spent: `@buildinternet/uploads` already ships
`sharp`, `roughjs`, `opentype.js`, `exif-reader`, `perfect-freehand`, and an
optional `playwright-core`. The v2 SDK's entire dependency tree is `zod` plus
`@modelcontextprotocol/core`.

Meanwhile the maintenance cost of hand-rolling rose sharply with this
revision. `2026-07-28` introduces multi-round-trip requests (MRTR), moves
tasks into an extension, replaces the GET stream and `resources/subscribe`
with `subscriptions/listen`, partitions the JSON-RPC error-code range, and
formalises a SEP process with twelve-month deprecation windows. The spec now
moves on a cadence, and every revision would be ours to implement and
conformance-check by hand.

The migration is also cheaper than sunny's, because v2 exports
`fromJsonSchema(schema, validator?)`, which adapts a raw JSON Schema into the
Standard Schema that `registerTool` expects. sunny rewrote their tool schemas
into zod because theirs were already zod under v1; ours are JSON Schema and
pass through unchanged.

Considered and rejected: authoring tools as AI SDK `tool()` objects (the shape
`packages/uploads/src/agent.ts` already uses via `files-sdk/ai-sdk`) and
adapting to MCP. The AI SDK's MCP support is client-side only —
`createMCPClient` consumes an MCP server and converts its tools _into_ AI SDK
tools. There is no server-authoring abstraction, and no shipped adapter in the
direction we need, so this would trade one bespoke layer for another while
coupling the CLI and the Worker bundle to `ai`. `agent.ts` already carries the
comment "do not duplicate MCP tool definitions here"; the separation is
deliberate and stays.

## Decisions

### `McpTool` stays the authoring format

`createMcpServer` keeps its signature and its `McpTool[]` input. Internally it
builds an SDK `McpServer` and registers each tool. This leaves ~2,400 lines of
tool definitions and all of `args.ts` untouched, keeps the published
`@buildinternet/uploads/mcp` export stable in shape, and confines the SDK to
one file.

The SDK validates against the JSON Schema first; our `args.ts` helpers
(`optString`, `optStringRecord` with its `__proto__` defense,
`canonicalMetaFromArgs`) still run inside handlers. That redundancy is
deliberate — the helpers do domain normalisation and produce tuned error
messages, not just type checks.

### The JSON Schema validator is injected per runtime

v2 does **not** auto-select a validator by export condition. The `workerd`
condition in its `package.json` applies only to `./_shims`; neither validator
provider is bundled into the root entry. Selection is explicit, via
`@modelcontextprotocol/server/validators/cf-worker` or `/validators/ajv`, and
`fromJsonSchema` takes the provider as its second argument.

This matters because the ajv provider compiles schemas with `new Function`,
which workerd rejects, and costs 268 KB besides.

So `createMcpServer` gains an injected `validator` option — additive, and it
preserves the core's runtime-agnostic promise. `apps/mcp` passes
`CfWorkerJsonSchemaValidator`; the CLI passes the ajv provider.

> Note: sunny's PR #774 states that "the SDK's `workerd` export condition
> auto-selects its non-eval JSON Schema validator at the consumer's bundle
> step." That is not what the published package does. Worth passing back.

### The worker routes the two eras explicitly

`createMcpHandler`'s built-in legacy fallback constructs its transport without
`enableJsonResponse`, so it answers with an SSE stream whenever the client's
`Accept` header permits one. Every current `agents.uploads.sh` caller receives
plain JSON today, and a migration must not silently change their wire shape.

Therefore, following sunny:

- `isLegacyRequest(request)` → a hand-wired
  `WebStandardStreamableHTTPServerTransport({ sessionIdGenerator: undefined,
enableJsonResponse: true })`, preserving today's plain-JSON reply body.
- otherwise → `createMcpHandler(factory, { legacy: "reject" })`, serving
  2026-07-28 traffic only. `legacy: "reject"` is an unreachable safety net,
  since `isLegacyRequest` has already claimed anything it would apply to.

**One legacy behaviour does change, and it is not avoidable via the SDK.** The
transport enforces the Streamable HTTP header requirements that our hand-rolled
core never checked — it read the body and answered. Measured against v2.0.0:

| Legacy request                                   | Before | After |
| ------------------------------------------------ | ------ | ----- |
| no `Accept: application/json, text/event-stream` | 200    | 406   |
| `Accept: application/json` only                  | 200    | 406   |
| no `Content-Type: application/json`              | 200    | 415   |

Both headers have been mandatory since protocol revision `2025-03-26`, so
conformant MCP clients already send them, but anything hand-rolled against
`agents.uploads.sh` will break. `scripts/smoke-remote-mcp.mjs` was one such
caller and is fixed in this change.

Deliberately not announced beyond `apps/mcp/README.md`: the hosted worker is
not a versioned or published artifact, so there is no release-notes channel to
put it in, and the affected population — hand-rolled callers that skip headers
the spec has required since early 2025 — is small enough not to justify
inventing one.

Both legs build from one `createMcpServer` call, so the 17-tool remote surface
cannot drift between eras.

### `handleLine` leaves the public interface

The SDK owns dispatch, so `McpServer` becomes transport-shaped instead.
`apps/mcp` is the only in-repo consumer, but `@buildinternet/uploads/mcp` is a
published subpath export, so this is a breaking change for the CLI package and
the changeset must say so plainly.

`packages/uploads/src/mcp/stdio.ts` is deleted; `commands/mcp.ts` moves to the
SDK's `serveStdio(factory)` from `@modelcontextprotocol/server/stdio`, which
owns era negotiation and connection lifecycle.

### `tools/list` cache hints

`{ ttlMs: 3_600_000, cacheScope: "private" }`. The catalog is static per
deploy, so a generous TTL is honest; it is auth-gated and, on the remote
surface, scope-filtered per token, so `private` — a shared intermediary must
not cache one caller's tool list for another.

### Authentication is untouched

`mcpBearerAuth` and `workspacePathAuth` (`apps/mcp/src/index.ts`) still run
before any MCP processing. The OAuth JWT lane, the `up_` token lane, the RFC
9728 discovery challenges, the `/:workspace/mcp` path route and its workspace
claim check, and the `mintingUserId` attribution all keep their exact
behaviour. `GET`/`DELETE` stay 405.

## What the SDK handles for us

The `_meta` envelope (`io.modelcontextprotocol/protocolVersion`,
`…/clientCapabilities`), `server/discover`, `Mcp-Method`/`Mcp-Name` header
validation and the 400 on absence, the required `resultType` on results, the
renumbered error codes (`-32020` HeaderMismatch, `-32021`
MissingRequiredClientCapability, `-32022` UnsupportedProtocolVersion), era
classification, and the legacy `initialize` handshake.

Our hand-rolled `ping` case disappears: `2026-07-28` removed the method, and
the legacy leg answers it for older clients.

## What we still own

- **The handler wrapper** — `recordEvent` telemetry (`surface: "mcp"`,
  duration, `errorCode`) and the `ToolBatchError` branch that preserves
  `structuredContent` on a multi-file total failure, so agents see every
  per-file error rather than only the first message.
- **Two server cards, currently duplicated** — `mcpServerCard()` in
  `apps/mcp/src/index.ts` and the static
  `apps/web/public/.well-known/mcp/server-card.json` both hardcode
  `protocolVersion: "2025-06-18"`. They must move together; that they can
  drift is a pre-existing wart worth fixing in this pass.
- **`scripts/smoke-remote-mcp.mjs`** — keeps its `initialize` leg pinned to a
  2025-era revision (legacy compatibility is the thing most worth smoking in
  production) and gains a modern-era leg. Per `docs/contract-testing.md` this
  runs against the protected `remote-mcp-smoke` GitHub Environment.
- **Docs** — `apps/mcp/README.md`, plus MCP mentions in `docs/cli.md` and
  `docs/api.md`.

## Testing

The 62 CLI tests migrate by rewriting the single `rpc()` helper at
`packages/uploads/test/mcp.test.ts:253`. The 64 `apps/mcp` HTTP tests are
legacy-era traffic and should pass untouched — which makes them the regression
signal that the legacy leg is genuinely byte-identical.

New modern-era coverage, mirroring sunny's: `tools/list` and `tools/call` with
the `_meta` envelope plus the required headers, a missing `Mcp-Method`
rejected as 400, and `server/discover`.

Verification gates: `pnpm test`, `pnpm check`, the `apps/mcp` typecheck, and
`pnpm --filter @uploads/mcp bundle:check` — the last one matters most, because
the validator question above is fundamentally a bundling question. Then the
prod smoke script against `agents.uploads.sh` on both eras.

## Out of scope

- **DCR → CIMD.** `2026-07-28` deprecates RFC 7591 Dynamic Client
  Registration in favour of Client ID Metadata Documents. We run
  `better-auth ^1.6.23` with `@better-auth/oauth-provider` and a stale-client
  reaper (`apps/auth/src/oauth-client-reaper.ts`), so CIMD is gated on our own
  1.6 → 1.7 upgrade — which carries the `Account.accountId` →
  `providerAccountId` rename, the `oauthApplication` → `oauthClient` table
  rename, and a reviewed D1 backfill. Tracked as its own issue, our analog of
  sunny's #778. DCR remains spec-valid through a ≥12-month deprecation
  window, so nothing is on a clock.
- **`subscriptions/listen`** — we have no change notifications to push.
- **MRTR / elicitation and the tasks extension** — no use case; both opt-in.

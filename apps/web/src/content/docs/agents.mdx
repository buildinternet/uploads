<section class="lead" id="install">

## Install <a class="anchor" href="#install" aria-label="Link to this section">#</a>

`uploads install` finds your agent runtime and adds the agent skills and the hosted MCP server:

```bash
uploads install
```

<div class="pointer">
  Using Claude Code or Codex? [Install the plugin](#plugin) instead.
</div>

<div class="pointer">
  Using claude.ai or Cowork? Add uploads from the
  [Claude directory](https://claude.ai/directory/uploads) instead.
</div>

### Or set up by hand

Add the skills:

```bash
npx skills add buildinternet/uploads
```

Then register the MCP server with your runtime:

<Tabs syncKey="agent-runtime">
  <TabItem label="Claude Code">

```bash
claude mcp add --transport http uploads https://agents.uploads.sh/mcp
```

  </TabItem>
  <TabItem label="Codex">

```bash
codex mcp add uploads --url https://agents.uploads.sh/mcp
```

  </TabItem>
  <TabItem label="Cursor">

Add it in Cursor's MCP settings, or in `.cursor/mcp.json`:

```json title=".cursor/mcp.json" frame="code"
{
  "mcpServers": {
    "uploads": { "url": "https://agents.uploads.sh/mcp" }
  }
}
```

  </TabItem>
  <TabItem label="OpenCode">

```bash
opencode mcp add uploads --url https://agents.uploads.sh/mcp
```

  </TabItem>
</Tabs>

<section id="plugin">

## Claude Code & Codex plugins <a class="anchor" href="#plugin" aria-label="Link to this section">#</a>

The plugin bundles the skills, the MCP server, the [pre-PR reminder](#pre-pr-reminder), and, in
Claude Code, [mods](#mods). In Claude Code, add the marketplace, then install:

```text
/plugin marketplace add buildinternet/uploads
```

```text
/plugin install uploads@uploads
```

Codex loads the same repo as a plugin. After you enable it, open `/hooks` once and trust the hook
if Codex asks.

The reminder hook calls the `uploads` CLI, so install it and run `uploads login` once.

</section>

<section id="instructions-file">

## Tell the agent to capture as it works <a class="anchor" href="#instructions-file" aria-label="Link to this section">#</a>

Add a block like this to your project's instructions file: `AGENTS.md`, `CLAUDE.md`,
`.cursor/rules`, or whatever your runtime reads.

```md title="AGENTS.md" frame="code"
## Screenshots
When a change is visible (UI, layout, styling), capture it as you go.
Don't wait for the PR. After each meaningful visual change:

  uploads put ./shot.png --meta path=/route --state after

On a branch, that stages the file for the PR. After opening the PR, run
`uploads attach --promote` to post everything staged. It's safe to run
even if the GitHub App already posted them.
```

For how staging works, see [Stage before a PR exists](/docs/attach-pull-request-images#staging).

<div class="note">
  Want the guided version? The [agent walkthrough](/github-screenshots) takes a coding agent from
  install to a first staged before/after.
</div>

</section>

<section id="pre-pr-reminder">

## Pre-PR screenshot reminder <a class="anchor" href="#pre-pr-reminder" aria-label="Link to this section">#</a>

Before `gh pr create`, the reminder hook nudges the agent if the branch touches UI files and
nothing is staged. When files are staged, it says whether they attach on their own when the PR
opens. If those files are older than 30 days, or they belong to a different branch, it suggests
`uploads unstage --branch <name>` instead. It never blocks the PR. Turn it off with
`UPLOADS_HOOK_DISABLE=1`.

- **Claude Code and Codex:** included in the [plugin](#plugin).
- **Grok and Cursor:** `uploads install` adds it when those tools are installed.

</section>

<section id="mods">

## Claude Code mods <a class="anchor" href="#mods" aria-label="Link to this section">#</a>

In Claude Code, the plugin also ships [mods](https://code.claude.com/docs/en/plugins/mods/overview):
code that runs inside Claude Code and can add to its interface. The plugin includes:

- **Staged media band:** shows the files staged for your branch above the prompt, and attaches them
  when `gh pr create` opens the PR.

Mods use the local `uploads` CLI, so install it and run `uploads login` once. Change their options,
such as the automatic attach, in `/plugin`. Mods need Claude Code 2.1.287 or later. Older versions,
Codex, and hosted MCP setups get the rest of the plugin.

</section>

<section id="skill-vs-mcp">

## Skill vs. MCP <a class="anchor" href="#skill-vs-mcp" aria-label="Link to this section">#</a>

The **skills** teach the agent when to capture and which `uploads` command to run. They need the
CLI.

The **MCP server** gives the agent upload tools directly. There are two:

| Server                                  | Use it when                     | Differences                                                                                                  |
| --------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Local, `uploads mcp`                    | The agent runs on your machine  | Same tools as the CLI, including `attach`.                                                                   |
| Hosted, `https://agents.uploads.sh/mcp` | The agent has no local checkout | No `attach` and no git defaults. Pass `repo` and `branch` to `put`, then call `promote` once the PR exists. `list_activity` and `list_repo_files` list recent tagged files by pull request or by repo, and only this server has them. |

For auth, scopes, and every tool's parameters, see the [MCP server reference](/docs/mcp).

To use the local server instead of the hosted one:

<Tabs syncKey="agent-runtime">
  <TabItem label="Claude Code">

```bash
claude mcp add uploads -- uploads mcp
```

  </TabItem>
  <TabItem label="Codex">

```bash
codex mcp add uploads -- uploads mcp
```

  </TabItem>
</Tabs>

<section id="experimental-ai-tags">

## Experimental: AI labels <a class="anchor" href="#experimental-ai-tags" aria-label="Link to this section">#</a>

<div class="note">
  Experimental and **off by default**. The uploads.sh team turns it on per workspace. To try it,
  open an issue on [the GitHub repo](https://github.com/buildinternet/uploads).
</div>

When it's on, uploads.sh labels each file shortly after it's uploaded. The labels never replace a
`path` or `state` you set, and a labeling error never fails the upload. A label it isn't confident
about is left off.

| Key             | Values                                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai.kind`       | `screenshot` `photo` `diagram` `document` `code` `ui` `other`                                                                                         |
| `ai.surface`    | `mobile` `desktop` `tablet` `unknown`                                                                                                                 |
| `ai.screen`     | `login` `signup` `settings` `profile` `dashboard` `analytics` `list` `detail` `form` `search` `modal` `onboarding` `empty` `error` `checkout` `other` |
| `ai.tags`       | Older uploads only. The current labeler does not write tags.                                                                                          |
| `ai.summary`    | Older uploads only. The current labeler does not write a summary.                                                                                     |
| `ai.classifier` | `v5` on the default labeler. A resized image writes `v6`. A Luna try writes `v4`. No image writes `skipped`. A failed call writes `failed`.                                          |
| `ai.skip`       | `small`, `unsupported`, `resize_failed`, or `resize_timeout`. Paired with `ai.classifier=skipped`. No model call, and no kind, surface, screen, or safety value. |
| `ai.error`      | `timeout`, `provider_error`, or `no_answer`. Paired with `ai.classifier=failed`. The model call ran and no label was stored.                               |

The same call also records four internal flags. They are not chips. They do not appear on the public file page, in a gallery, in a feed, in an embed, or in a pull request comment. They do not change who can view the file.

| Key                     | Values                                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai.rating`             | `safe` `suggestive` `explicit`                                                                                                                  |
| `ai.content`            | `none` `sexual` `violence` `gore` `drugs` `hate` `self_harm` `other`                                                                            |
| `ai.secret`             | `none` `api_key` `password` `private_key` `token` `connection_string` `other`. A credential that grants access. A name or an email is not one. |
| `ai.pii`                | `none` `contact` `identity_document` `financial` `other`. A signed-in name or email in a header stays `none`.                                   |
| `ai.rating.confidence`  | `high` at 0.85 or above. `medium` from 0.70 up to 0.85. `low` from 0.50 up to 0.70.                                                             |
| `ai.content.confidence` | Same buckets as `ai.rating.confidence`.                                                                                                         |
| `ai.secret.confidence`  | Same buckets as `ai.rating.confidence`.                                                                                                         |
| `ai.pii.confidence`     | Same buckets as `ai.rating.confidence`.                                                                                                         |

An answer under 0.50 is left off, and so is its confidence key. `ai.secret` and `ai.pii` stay separate, so a broad personal-data hit does not hide a real credential.

A stored flag stays until a later classification writes that same key. A confident `none` replaces the old value. An answer under the floor, a model timeout, or an error leaves the previous flag in place. A skip writes no safety value, so it does not replace or restore one. Re-uploading identical bytes does not clear a flag. New bytes start fresh, and a skip on those bytes leaves the flags clear.

The classifier version does not change for these flags. `v5`, `v6`, `v4`, and `skipped` still name how the image was prepared. A file labeled before the flags existed simply has none of these keys.

Labels aren't in the upload's response. Read them afterward, or search by them:

```ansi
uploads meta get <key>              # one file's labels, including internal flags
uploads find ai.screen=login        # files with a label
uploads find ai.secret=api_key      # internal flag; workspace members only
```

From an MCP client, use `get_metadata` and `find_files`. Clients can't set or delete `ai.*` keys.

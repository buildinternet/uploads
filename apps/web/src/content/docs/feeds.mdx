<section class="lead" id="what">

## What a live link is <a class="anchor" href="#what" aria-label="Link to this section">#</a>

A live link is a public page of the files already tagged with a GitHub repo. With a live link you
can:

- Share the latest files for a repo behind one `/c/<id>` URL.
- Scope the same link to one pull request or issue.
- Open one file at `/c/<id>/<item>` and page through the set.
- Filter by page path (the same `path` metadata `uploads find` uses).

A live link updates on its own: new tagged files appear without anyone adding them. To hand-pick
and order a set instead, use a [gallery](/docs/galleries). See [Live link or gallery](#when).

Anyone who knows the URL can view the live link. GitHub repository visibility does not restrict it.

<div class="note">
  The CLI, API, and MCP call a live link a <strong>feed</strong>. <code>uploads feed create</code>,
  MCP <code>feed_create</code>, and the <code>/feeds</code> REST routes all create or read one, and
  its URL starts with <code>/c/</code>.
</div>

</section>

<section id="create">

## Create a live link <a class="anchor" href="#create" aria-label="Link to this section">#</a>

Create a repo-wide live link. This prints its public URL. Pass `owner/repo` or `--repo`. Omit both
and the CLI uses the current git remote:

```bash
uploads feed create owner/repo
uploads feed create --repo owner/repo
```

Creating the same scope again returns the existing URL. A workspace holds up to 50 repo-wide live
links. Pull request and issue live links have no cap.

<div class="pointer">
  Want only one pull request? Add <code>--pr</code>, or pass <code>--github</code> with
  <code>owner/repo#123</code> or a GitHub URL. <code>--issue</code> does the same for an issue.
  Optional <code>--path</code> keeps the link to one page path.
</div>

Open an existing live link with `uploads feed show`.

<div class="note">
  From a hosted agent (no local CLI), call MCP <code>feed_create</code> with <code>repo</code>, plus
  <code>pr</code> when the link should stay on one pull request. <code>github</code> alone can
  supply both. <code>feed_get</code> returns the current files and the public URL.
</div>

</section>

<section id="comment">

## The PR comment <a class="anchor" href="#comment" aria-label="Link to this section">#</a>

Syncing the managed PR comment creates the pull request's live link if it does not exist yet. The
comment then opens with a line like `12 files · View all on uploads.sh →` that links to it.

Each file tagged with that pull request links to its own page in the live link. A file whose
`gh.*` metadata names a different pull request keeps its `/f/` link. The `<img>` still loads from
the embed URL.

The comment posted through your local `gh` (no GitHub App on the repo) shows the same line and
links. Turn both off with `linkToFilePage: false` in [`.uploads.yml`](/docs/comment-config).

</section>

<section id="pager">

## Page through the set <a class="anchor" href="#pager" aria-label="Link to this section">#</a>

The live link page shows 50 files at a time, newest first. **Older files** opens the next page.

Each file has its own page at `/c/<id>/<item>`, with newer and older links and a 1 of N count. Older
`/feed/…` links redirect to `/c/…`.

Standalone `/f/…` pages stay for one-off shares.

</section>

<section id="when">

## Live link or gallery <a class="anchor" href="#when" aria-label="Link to this section">#</a>

Use a live link when you want to follow what changes. Use a [gallery](/docs/galleries) when you
want to choose what people see.

| | Live link | Gallery |
| --- | --- | --- |
| **What's in it** | Every file tagged with the repo, or one PR or issue | Only the files you add |
| **Order** | Newest first | The order you choose |
| **Upkeep** | None. New files appear on their own. | Add each file with `--gallery` |
| **Use it for** | Following a repo or PR as it changes | A release, demo, or review set |

A repo live link and a PR live link are the same thing with one extra filter.

</section>

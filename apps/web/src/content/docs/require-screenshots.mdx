<section class="lead" id="how-it-works">

## How it works <a class="anchor" href="#how-it-works" aria-label="Link to this section">#</a>

Once the [uploads.sh GitHub App](/docs/github-app) is installed, a check called **Check for visuals** shows up
in a pull request's checks whenever the PR changes UI files. It sits next to your tests and builds,
and looks for screenshots or recordings on the PR from your coding agent, the
[uploads CLI](/docs/attach-pull-request-images), or images dragged into the PR on GitHub.

Out of the box the check only reports. It goes neutral ("UI changed, no visuals attached"), so
nobody is blocked or notified. Turn on a requirement and it fails until the screenshots are there,
then passes on its own when they arrive. Make it a required check in GitHub and it works like a
linter for UI changes.

No CI workflow or GitHub Actions step is needed. The check comes from the GitHub App, the same way
other GitHub integrations post theirs, and it re-runs on each push, each new upload, and each
approval.

<div class="note">
  The check is built around screenshots and screen recordings today. Other file types, like test
  reports and logs, may get their own checks later.
</div>

</section>

<section id="basic">

## Basic setup <a class="anchor" href="#basic" aria-label="Link to this section">#</a>

Make sure every pull request that changes your UI has at least one screenshot or recording:

1. **Install the GitHub App** on the repository from <a href={GITHUB_APP_INSTALL_URL}>GitHub</a>.
   The check starts reporting right away.
2. **Turn on the requirement.** A workspace admin can switch on **Require screenshots on UI
   changes** under **Settings → GitHub** in uploads.sh, for every repo in the workspace. Or commit
   this to one repo's [`.uploads.yml`](/docs/comment-config):

   ```yaml title=".uploads.yml" frame="code"
   comment:
     check:
       require: [uploads]
   ```

3. **Make it required in GitHub.** In the repo's **Settings → Branches** (or **Rules**), require
   status checks to pass before merging and add `Check for visuals`. GitHub only lists a check after
   it has run once, so open or update a pull request first. The check used to be called
   `uploads.sh`; if a rule still requires that name, swap it for the new one.

With a requirement on, every pull request gets the check, and one that changes no UI files passes
straight away.

</section>

<section id="ui-files">

## Which files count as UI <a class="anchor" href="#ui-files" aria-label="Link to this section">#</a>

By default, changes to `.astro`, `.tsx`, `.jsx`, `.vue`, `.svelte`, `.html`, `.css`, `.scss` and
`.less` files, and anything in an `email/` folder. It's the same list the CLI's
[pre-PR reminder](/docs/agents#pre-pr-reminder) uses. Deleted files, and files moved without edits,
don't count.

To choose the files yourself for every repo in a workspace, list them under **UI file paths** in
**Settings → GitHub**. One repo can set its own list under `uiPaths`, which replaces the workspace
list:

```yaml title=".uploads.yml" frame="code"
comment:
  uiPaths:
    - "apps/web/**"
    - "*.css"
```

A pattern without a slash matches a file name anywhere. One with a slash starts at the repo root.
`uiPaths: []` turns the check off for that repo.

</section>

<section id="more">

## Ask for more than one screenshot <a class="anchor" href="#more" aria-label="Link to this section">#</a>

List what every UI change should include. The PR comment shows a checklist that ticks itself as files
arrive, the check's summary repeats it, and the check passes once every item is ticked:

```yaml title=".uploads.yml" frame="code"
comment:
  check:
    require: [before-after, desktop, mobile]
```

<table>
  <thead>
    <tr>
      <th>Item</th>
      <th>Passes when</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>
        <code>uploads</code> (or <code>any</code>)
      </td>
      <td>The PR has at least one upload. Every other item implies it.</td>
    </tr>
    <tr>
      <td>
        <code>before-after</code>
      </td>
      <td>
        There's a capture uploaded with <code>--state before</code> and one with{" "}
        <code>--state after</code>.
      </td>
    </tr>
    <tr>
      <td>
        <code>desktop</code>, <code>mobile</code>
      </td>
      <td>
        There's a capture of each. The AI label decides when it's set, otherwise the frame's shape
        (tall reads as mobile, wide as desktop).
      </td>
    </tr>
  </tbody>
</table>

A repo's `check.require` replaces the workspace's **Require screenshots on UI changes** switch.

</section>

<section id="what-counts">

## What counts <a class="anchor" href="#what-counts" aria-label="Link to this section">#</a>

- **Files uploaded with uploads.sh**, from the CLI, the [MCP server](/docs/mcp), or an agent,
  including ones [staged before the PR existed](/docs/github-app#staging).
- **Images and videos dragged into the PR on GitHub**, in the description or a comment. Links to
  images committed to the same repo (`blob/…/shot.png?raw=true`) count too. These pass `uploads`,
  so contributors without uploads.sh are never stuck. The other items need files uploaded with
  uploads.sh.
- **Held files.** A file [held for review](/docs/github-app#held-files) counts as attached, so a
  hold never blocks a merge.

</section>

<section id="skip">

## Skip a pull request <a class="anchor" href="#skip" aria-label="Link to this section">#</a>

A PR that needs no screenshots can skip the requirement with a label: `uploads:skip-verify`,
`skip-uploads`, or `uploads-skip`, in any case. The check turns neutral right away, and the comment
says the requirement was skipped and by which label. A repo can list its own labels instead:

```yaml title=".uploads.yml" frame="code"
comment:
  check:
    require: [uploads]
    skipLabels: ["no-screenshots"]
```

</section>

<section id="ai-notes">

## AI notes <a class="anchor" href="#ai-notes" aria-label="Link to this section">#</a>

AI notes are a second look at the screenshots themselves. They show up under the checklist in the
check's summary and in the PR comment, and a warning is named in the check's title. They never fail
the check.

```yaml title=".uploads.yml" frame="code"
comment:
  check:
    ai: all
```

<table>
  <thead>
    <tr>
      <th>Note</th>
      <th>Warns when</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>
        <code>ready-screen</code>
      </td>
      <td>
        A capture uploaded with <code>--state after</code> looks like it is still loading, blank, or
        showing an error. Before captures are never judged, since a broken screen is a fine before.
      </td>
    </tr>
    <tr>
      <td>
        <code>identical-before-after</code>
      </td>
      <td>A before and an after are the same picture.</td>
    </tr>
  </tbody>
</table>

Each note says ok, warning, or skipped. A note is skipped with a reason when it has nothing to look
at, like no files marked as after. The notes read the [AI labels](/docs/ai-labels)
uploads.sh adds to each image, so they need AI labels on for the workspace. Add the
`uploads:no-ai` label to a PR to hide them.

</section>

<section id="no-uploads-comment">

## The how-to comment <a class="anchor" href="#no-uploads-comment" aria-label="Link to this section">#</a>

Once UI file paths are set for the workspace or repo, a pull request that changes one of those files
with nothing attached also gets a short comment. It names the changed files and the ways to add
screenshots. It's the same managed comment the App keeps on every PR, so the first upload replaces
it with the normal screenshots.

To keep the check but skip the comment, a workspace admin can turn off **Comment when a PR has no
uploads** under **Settings → GitHub**, or a repo can set `noUploadsComment: false`.

</section>

<section id="web-settings">

## Manage it from uploads.sh <a class="anchor" href="#web-settings" aria-label="Link to this section">#</a>

Workspace admins can change these under **Settings → GitHub** without touching any repo:

- **Require screenshots on UI changes**: fail the check on UI changes with nothing attached.
- **UI file paths**: which files count as UI changes.
- **Comment when a PR has no uploads**: the [how-to comment](#no-uploads-comment).

Each applies to every repo in the workspace. A repo's [`.uploads.yml`](/docs/comment-config) wins
where it sets the same thing, and the settings page shows which repo values are in effect.

</section>

backend-only PRs stay quiet.

<section id="troubleshooting">

## Troubleshooting <a class="anchor" href="#troubleshooting" aria-label="Link to this section">#</a>

- **No check on the PR.** The App isn't installed on the repo, or the PR changes no UI files and no
  requirement is on. If your org installed the App before checks existed, an org admin has to
  approve the new Checks permission first. See [Permissions & events](/docs/github-app#permissions).
- **`Check for visuals` isn't listed in branch protection.** GitHub lists a check only after it has run on
  the repo once. Open or update a pull request, then add it.
- **A mobile capture reads as desktop.** Without an AI label, the shape decides. Crop a phone capture
  to its viewport, or use `uploads screenshot --frame` for device chrome.
- **A PR is skipped by mistake.** Remove the skip label and the check re-evaluates.

</section>
